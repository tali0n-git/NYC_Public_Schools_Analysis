# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Role in this project

This is a data science / research project, not a software product. When working here, act as an ML/analytics collaborator:
- Sanity-check statistical and ML methodology before implementation (leakage, confounding, appropriate train/test splits, ordinal-vs-categorical treatment of ratings, spatial autocorrelation).
- Prefer explaining *why* a technique fits (or doesn't) over silently writing code.
- Flag when a claimed "insight" is really correlation without a plausible causal story — this project's stated goal is to bring findings to City Council/MTA/DOE, so overclaiming has real consequences.
- Default to notebook-based, exploratory workflow already in use here (see Notebook Execution Order below) rather than introducing a separate script/pipeline framework unless asked.

## Project summary

Investigates whether NYC public school **Quality Review (QR) ratings** correlate geographically/temporally with **MTA subway on-time performance**, at the ZIP/Census-tract/Community-District level. Full narrative and data source links live in [README.md](README.md) — read that first for the research question and data dictionaries.

None of the CSV/JSON files under those three folders are committed. This means:
- A fresh clone of this repo has notebooks but no data — the raw NYC OpenData / data.ny.gov files (linked in README.md) must be downloaded manually into `data/`, and `cleaned_data/` must be regenerated by running the cleaning notebooks in order.
- Never assume `cleaned_data/*.csv` is up to date with the notebook that produced it — check whether the notebook has been edited since the file was last written before trusting it as ground truth.

## Notebook execution order (data lineage)

The notebooks are the ETL scripts. They must run in this order because each stage reads the previous stage's output from `cleaned_data/`:

1. `School_Data_Analysis_Notebooks/SchoolLocationData_EDA.ipynb` → `cleaned_data/location_data.csv`
   - Cleans `data/LCGMS_SchoolData_*.csv`, fuzzy-matches malformed `City` values to boroughs (`thefuzz`), drops non-five-borough rows, joins **ZIP-code centroid** lat/lng from `us_zip_codes.csv`.
2. `School_Data_Analysis_Notebooks/QualityReviewRatings_2005-2020_EDA.ipynb` → `cleaned_data/{Borough}_yearly_ratings.{csv,json}`, `AllBoroughs_yearly_ratings.csv`, `QualityReviewRatings_Cleaned.csv`
   - Converts Excel serial dates, maps letter ratings to an ordinal 0–8 scale (`ratings_rank`), reads `location_data.csv` from step 1, backfills missing school locations from a secondary export (`LCGMS_SchoolData_2025_2.csv`).
3. `MTA_Data_Analysis_Notebooks/MTA_Subway_Stations_EDA.ipynb` → `cleaned_data/MTA_Subway_Stations_w_Tracts+Zip_2025.{csv,json}`
   - Joins ZIP via KDTree nearest-centroid, geocodes Census tracts via the Census Bureau API (`censusgeocode`, ~8–9 min run).
4. `MTA_Data_Analysis_Notebooks/MTA_On-Time_Performance_EDA.ipynb` → `cleaned_data/MTA_Subway_Performance.{csv,json}`
   - Concatenates the 2015–2019 and 2020–2024 on-time performance datasets; reconciles line-naming differences between eras (see Data Caveats).
5. `MTA_Data_Analysis_Notebooks/MTA_Subway_Groupings.ipynb` → `cleaned_data/MTA_Subway_Grouped_Data.{csv,json}` (reads outputs of steps 3 and 4)
   - Explodes multi-route stations, resolves shuttle (`S`) lines to `GS`/`FS`/`RS` by borough, groups stations by line and attaches monthly performance metrics.
6. `ML_Notebooks/k-means-tests.ipynb` (reads outputs of steps 2 and 5)
7. `ML_Notebooks/random-forest-tests.ipynb` — **currently broken/stub**, see below.

## Data caveats (read before trusting a merge or a metric)

- **School lat/lng is a ZIP-code centroid, not a geocoded address.** Every school in the same ZIP shares identical coordinates. Any distance-based join (e.g., nearest-subway-station) is only as precise as ZIP-code granularity — fine for borough/neighborhood-level patterns, not for block-level claims.
- **Census tracts don't line up 1:1 between the school and MTA datasets** (noted directly in `k-means-tests.ipynb`) — this is why the current clustering approach fell back to a lat/lng radius search (BallTree, haversine, 1.2-mile radius) instead of a tract/ZIP join. If tract-based joins are revisited, expect to reconcile 2010 vs. 2020 tract boundary vintages.
- **Subway line naming is inconsistent across eras and datasets** and requires manual reconciliation, already handled in the notebooks:
  - 2015–2019 performance data has no `J`/`JZ` distinction (only `JZ`); 2020+ splits them.
  - Shuttle lines appear as `S Fkln`, `S 42nd`, `S Rock`, and (2020+) `H` — remapped to `FS`, `GS`, `RS` respectively.
  - Staten Island Railway (SIR) has no associated on-time performance metrics and is effectively dead weight in any feature matrix that includes it — one commit explicitly tested removing it because of imbalanced clustering.
- **QR `overall_rating` letter codes are ambiguous.** The notebook's own data dictionary flags that even LLM-assisted lookups (Claude, Gemini) disagreed on what codes like `UD`, `UPF`, `DYO` mean, and that the rating scheme changed across eras (legacy Progress Report grades vs. the newer Quality Review rubric). The current `ratings_rank` ordinal mapping (`O`=8 ... `No Data`=0) is a working assumption, not a verified DOE-sourced crosswalk — treating `No Data` as `0` on the same scale as real ratings will bias any mean/regression that doesn't first filter it out.
- **~14.1% of schools (268/1,901) are missing or partially missing QR data**, and location backfill required manual aggregation logic for schools whose `bn` maps to multiple `Location Code`s (ratings get associated with an aggregated name — see `agg_add_schools` in the QR notebook — there isn't a clean 1:1 school-to-rating mapping for every row).
- **~9–10% of schools have no subway station within 1.2 miles** (see `k-means-tests.ipynb` cell computing `percent_no_subway`) — decide explicitly whether to drop these or keep them as a "no transit access" category; silently including them with all-zero one-hot vectors biases distance-based clustering toward a phantom "no train" cluster.

## Current ML state

- **K-means (`ML_Notebooks/k-means-tests.ipynb`)**: features are (a) one-hot encoded nearest subway lines within 1.2 miles and (b) standardized QR assessment-time epoch. k=9 chosen via elbow + silhouette (both plotted together in `images/elbow_silhouette_kmeans.png`). PCA(2) used only for visualization, not for clustering itself.
  - **Gap: the actual MTA on-time performance percentage is not yet a feature.** The clustering currently groups schools by *which* lines are nearby and *when* they were assessed — not by how well those lines performed. The stated notebook goal ("Use train performance as a predictor of school performance") isn't implemented yet; `MTA_Subway_Grouped_Data` already carries `mta_performance_data` per line and is loaded in the notebook, but it isn't merged into the feature matrix `X`. This is the most direct next step toward the project's actual research question.

Treat this as a placeholder for the intended supervised approach, not working code.

## ML best-practice notes for this project

- **This is fundamentally a supervised prediction/correlation question** ("does transit performance predict school ratings?"), not an unsupervised discovery question. K-means is useful for exploratory grouping, but the random forest (or a regression: OLS/mixed-effects with QR score as the outcome) is the more direct way to answer the actual research goal — prioritize getting on-time performance into a real feature matrix over further unsupervised tuning.
- **Watch for spatial and temporal autocorrelation.** Schools in the same neighborhood/line share transit exposure and often socioeconomic conditions; a naive train/test split will leak information across nearby schools. Consider grouped/spatial cross-validation (group by ZIP, tract, or borough) rather than a random split.
- **Confounding is the central risk to any headline claim.** QR ratings plausibly correlate with school funding, student poverty rate, staffing, and neighborhood demographics — all independent of transit. The unused Census demographic/population-change data one level up (`../Census_Data_Analysis_Notebooks/`) is the natural source of covariates to control for before attributing any transit correlation causal weight. Without at least one socioeconomic control variable, any MTA-vs-QR correlation is one confound away from being spurious.
- **Don't drop `QR Score = 0` / `No Data` silently.** Confirm whether "0" means "rated 0" or "missing" (per the caveats above, it's the latter) before it flows into a mean, regression target, or clustering feature — it currently would deflate averages.
- **The 1.2-mile radius and k=9 are both empirical/eyeballed choices**, not validated against the outcome variable. If the analysis moves to a supervised model, treat radius as a tunable hyperparameter (validate against QR score prediction error) rather than a fixed constant carried over from the unsupervised phase.
- Given the small, tabular, low-dimensional feature space here, favor interpretable models (linear/mixed-effects regression, random forest with feature importances, or SHAP if going further) over anything that trades interpretability for marginal accuracy — the deliverable is a policy narrative for City Council/MTA/DOE, and interpretability is what makes a recommendation defensible.
